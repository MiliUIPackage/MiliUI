**在 `QUEST_DETAIL` 裡直接呼叫 `AcceptQuest()` 會失敗**，而且失敗得很難認：
不報錯、伺服器不送任何訊息、任務視窗閃一下就關、任務沒進日誌。

**延後約 0.5 秒再按就穩定。**（2026-08-30 實測：0 / 0.25 秒失敗，0.5 / 1 / 3 秒成功。）

## 病徵

同一條任務**第一次必定失敗、第二次必定成功**；放棄之後重演；手動點永遠第一次就成功（人手移動滑鼠至少要一秒）。
實測案例是週任「至暗之夜：阿塔烏特克寶庫」(98232)，但成因跟任務本身無關。

## ⚠ 六個看起來很合理、但實測都錯的假設

| 假設 | 被什麼打掉 |
|---|---|
| `QuestGetAutoAccept()` 殘留，害我們走 `CloseQuest()` | 旗標兩次都是 `false` |
| 對話／多選一的選取邏輯有問題 | 那條任務**完全沒有 `GOSSIP_SHOW`**，直接 `QUEST_DETAIL` |
| 我們搶在暴雪的 `QuestFrame` 前面，詳情頁還沒建好 | 兩次的 `QuestFrame:IsShown()` 與接受鈕的顯示／可按都是 `true`；延後一幀也沒改善 |
| 合成點擊 vs 硬體點擊（`btn:Click()` 不算數） | 等 3 秒之後我們自己按也會成功 |
| 獎勵資料還沒到齊 | 失敗與成功那兩次的 `GetNumQuestChoices` / `GetNumQuestRewards` / `GetQuestMoneyToGet` 完全一樣 |
| 任務資料非同步載入（`RequestLoadQuestByID` ＋ `QUEST_DATA_LOAD_RESULT`） | 那個事件在 **0.00 秒**就回 `success=true` |

**客戶端看得到的東西兩次完全一致，唯一能改變結果的是時間。** 有一個**只有伺服器知道的暖機**，客戶端沒有任何訊號可以事先判斷
—— 所以只能延遲，沒有「等訊號」的漂亮解法。

## 實作的形狀（`MiliUI_QuestTracker/Modules/AutoQuest.lua`＋`Core/DB.lua`）

**不能事先知道哪條任務要等，但可以事後知道。** 預設秒接 → 按完 `VERIFY_AFTER`（0.5s）查任務日誌 → 沒進日誌就把 `questID` 記進
**帳號層級**的 `slowQuests`（週任每隻分身都要跑）、下次先等 → 還是不行才把**共用的** `acceptWait` 加 `WAIT_STEP` 0.1（`BASE_WAIT` 0.5～`MAX_WAIT` 2.0）。

- **秒數是所有任務共用的，只有「哪些任務需要等」是逐條記的**：延遲的成因是玩家連線的性質，不是某條任務的性質；任何一條學到的其他任務直接受惠。
- ⚠ **只有「這一次真的等過、還是沒接到」才往上加**（2026-10-01 `7134ba3b3`）：判斷看**按下去那一刻**有沒有等（`waited` 參數），不是查勤時這條在不在清單裡——
  秒接失敗的那一刻起它就在清單裡了，拿清單判斷會把「第一次秒接失敗」跟「等過還失敗」混在一起，每條新任務都把共用秒數養大一階。秒接失敗只代表「這條需要等」。
- **加到上限還不行就代表成因不是等待時間**，再加只是讓玩家更慢。
- 查勤 0.5 秒是為了讓玩家**還站在 NPC 面前**時就知道要再點一次；判定看日誌不看計時器，所以調短不會把成功誤判成失敗（除非伺服器真的慢過它，那本來就該等）。
- **`questID` 讀不到時退成 0 照樣按，但 0 不是鑰匙**（2026-09-20 `f88583f2f`）：查勤與學習整套都拿 questID 查日誌，`InLog(0)` 永遠 nil ⇒ 接成功了照樣罵玩家接失敗、
  還把 `[0] = true` 記進清單（實測玩家存檔裡出現過）。questID 為 0 時接完直接收工，不排查勤；載入時正規化順手把 `<= 0` 清掉。
- **內建種子清單**（`DB.lua` 的 `slowQuests` 預設值，2026-08-30 起四批、15 條）：原本以為「週任 ID 每週換、寫死清單隔週過期」，實測是**輪替**，蒐集幾輪就湊得齊，值得內建。
  收錄判準只有一個：**實測秒接接不到**（93598「征戰使節」不屬於至暗之夜那組照樣失敗，別拿名字開頭當判準）。每條帶任務名註解，否則下次無從判斷「還在不在輪替裡」。
  `MergeDefaults` 對值只補 nil ⇒ 玩家手動移除過的要靠 `dismissedSlow` 擋著，不然「移除了、下次登入又冒出來」（nil-merge 分不出「沒有過」跟「刪掉了」）；
  它只擋內建預設值，真的又接失敗時 Escalate 會清掉重新學——「我不要你預設塞給我」跟「量出來就是會失敗」是兩件事，後者該贏。
- 清單欄位的格式改過三次（true → 時間戳 → 逐條秒數 → 只存「要不要等」），**在入口正規化一次**（`NormalizeSlowList`），不要只在讀取時臨時換算
  （值永遠不會被寫回去，`/mquest slow` 就一直顯示舊格式換算出來的怪數字，實際回報過「98232=0.00s」）。

## 通則

- **狀態相同而結果不同 ⇒ 找時序，不要繼續找狀態。** 前三個假設都在找「哪裡不一樣」，而根本沒有不一樣。
- **排除一個方向之前，先確認自己的推論沒有踩到未驗證的前提。** 一度用「第二次也只等一幀卻成功」排除「等太快」，那建立在「就緒窗口每次各自計算」這個從沒驗證過的假設上。
- **要聽伺服器講話。** `UI_ERROR_MESSAGE` / `UI_INFO_MESSAGE` 應該一開始就掛上去。（這次沒說，那本身也是資訊。）
- **對照組要能區分變因。** 「關掉自動接、手動點」證明是我們造成的；「開著自動接、拉長延遲、手動點」才證明不是我們其他程式碼弄壞的。
- **不要把少數任務的成本攤到全部任務上。** 「一律先等 0.5 秒」練等時每條都慢半拍看得出來。
- **量出來的常數不是普世常數。** 0.5 是在某一條連線上量的，只能當起點與下限，讓它各自收斂。
- **學習機制要分清「觸發條件」與「調整量」的證據**：一次失敗只證明「需要等」，證明不了「等得不夠」；拿錯證據調參數會單調漂移。

## 別的插件

同一個寫法（`QUEST_DETAIL` 進來直接 `AcceptQuest()`、零延遲）在 **EllesmereUI** 與 **Leatrix Plus** 都是這樣，兩支都會中。
**ElvUI 沒有自動接任務功能**。Reddit 與各開發者論壇搜不到討論——這個失敗不報錯也不留訊息，看起來只像「偶爾沒接到」。
